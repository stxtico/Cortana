# A22 — Grounding upgrade + screen awareness (Steps 1-3 done: benchmark, UIA fix, model swap, narrow arbitration, post-action verification)

Moved verbatim-in-spirit from this session's work (2026-08-12/13) — see
CLAUDE.md's Done log for the one-line pointer back to this file.

## Why this phase changed shape from earlier guidance

Earlier guidance in this project treated "vision fabricates" as a flat
property of vision as a category. That was too broad. General-purpose VLMs
are unreliable at GUI grounding specifically, but purpose-built grounding
models are a different class of thing: on ScreenSpot-Pro (expert targets in
Photoshop/AutoCAD/VSCode/Blender), GPT-4o scores 0.8% and a 7B specialist
scores ~50% — beating a 72B generalist at a fraction of the size. A14's
finding (this project's own `gemma3:12b` fabricating specific wrong claims,
and separately producing a real false negative on a CAD render) was about
that specific general-purpose model doing a task it wasn't trained for, not
proof that vision-based grounding is inherently unreliable as a category.

## Step 1 — benchmark grounding specialists on real screens, not published numbers

**Two candidates, both feasible to run locally via Ollama — verified, not
assumed.** GTA1-7B (Salesforce, Qwen2.5-VL-based, dataset CC-BY-NC-SA / code
repo has no license file — fine for personal local use, a real constraint if
this ever ships) and Holo2-8B (H Company, Apache 2.0, Qwen3-VL-based).
Checked GGUF availability first (`mradermacher/GTA1-7B-GGUF`,
`mradermacher/Holo2-8B-GGUF`, both with mmproj files) and found a real risk
before downloading anything further: a live GitHub issue
(`ollama/ollama#14730`) reports "unknown model architecture" failures
specifically for custom-imported Qwen3-VL-family GGUFs with a separate
mmproj — the officially-listed `qwen3-vl:8b` in Ollama's library is a
first-party integration; a third-party fine-tune imported by hand isn't
guaranteed the same treatment. Tested directly rather than trusting the
concern or the docs: `ollama create` (`FROM ./model.gguf` + `ADAPTER
./mmproj.gguf`) succeeded for both, and — per A14's own lesson that
model-creation "success" and working vision are not the same claim — verified
with a real inference call against a real screenshot before trusting it
further. Both correctly read real on-screen text (`MODEL: GEMMA3-12B`,
`Tools/Activity`, `Latency`, `Memory`) in that check.

**A real 33-target benchmark, not a synthetic one.** Built from real, live
screenshots of five apps actually running on this machine (File Explorer, VS
Code, Chrome, Windows Terminal, and cortana's own Electron control panel —
picked deliberately over a narrower "Explorer + VS Code" set, since Chrome
and VS Code are exactly where custom-drawn controls defeat the accessibility
tree, the honest test of a fallback tier). Ground truth was never eyeballed:
sourced from live UI Automation tree enumeration (walking real element
rectangles via `pywinauto`, the same mechanism `tools/_computer_uia.py`
itself uses) for Explorer/VS Code/Chrome/Terminal, and from real DOM
`getBoundingClientRect()` queries over Chrome DevTools Protocol (the control
panel relaunched with `--remote-debugging-port`) for the Electron app, which
returned **zero** UI Automation elements at all — a genuine UIA-blind app,
exactly the case the grounder fallback exists for. Deliberately included hard
cases (icon-only toolbar buttons, small window-chrome controls) alongside
labeled/easy ones, split roughly half and half (14 easy / 19 hard), per the
explicit warning that a test set of large labelled buttons reports a number
that doesn't survive contact with real use — icon-only targets score under 5%
on ScreenSpot-Pro.

A first capture pass had a real, caught bug: `win32gui.SetForegroundWindow()`
called bare (no synthetic-input trick) failed silently for one window mid-
loop, and the resulting screenshot showed a *different* app's content bled
through on top of the target window — proof positive of the exact Windows
foreground-lock behavior A18 already documented, hit again by not reusing
A18's own fix. Rebuilt the capture step to call `tools/_computer_uia.py`'s
`focus_window()` (the real, verified fix) and refuse to save a screenshot at
all unless the actual foreground window matches the target — caught and
discarded the contaminated capture before it could corrupt ground truth.

**Results, using each model's own documented prompt/output format** (GTA1: a
system prompt stating the exact image resolution, raw `(x,y)` output; Holo2:
a JSON schema, `x`/`y` normalized 0-1000, converted back to pixels against
the real image dimensions):

| | Overall (33) | Easy (14) | Hard (19) |
|---|---|---|---|
| **GTA1-7B** | **81.8%** | 100.0% | 68.4% |
| **Holo2-8B** | 51.5% | 85.7% | 26.3% |

**The published ranking inverted on real screens — the strongest evidence yet
for the "benchmark on your own screens" rule, worth citing by name next time
a paper spec is tempting.** Holo2-8B leads GTA1-7B on ScreenSpot-Pro (58.9%
vs 50.1%, per H Company's own model card) but lost by 30 points here (51.5%
vs 81.8%), with the widest gap specifically on hard targets (26.3% vs
68.4%). A benchmark run against someone else's screens picked the wrong
model for this one, decisively — not a close call that random variance could
explain.

## A real bug found underneath the UIA baseline, not just a number reported

Raw UIA exact-name resolution across the 33 targets came back 39.4% at
first — but per this project's own A21 lesson ("if a check passes, be sure
you know why it passed" applies just as much to why a check *fails*),
that number was checked, not trusted. Broken down by app it was 100% on
Explorer and Terminal (single-process apps) and **0% on VS Code, Chrome, and
cortana's own control panel** — not because those apps lack real
accessibility structure (direct enumeration found 120 real elements in VS
Code, 61 in Chrome, both with genuine accessible names for the very icons
being tested) but because `tools/_computer_uia.py`'s `resolve()` used
`pywinauto.Application().connect(path=process_match)`, which raises
`ProcessNotFoundError` outright — not "picks a wrong process," total failure
— for any app that spawns multiple processes sharing one executable name
(VS Code, Chrome, and every Electron app, including cortana's own UI, all
do this via renderer/helper/GPU child processes). `explorer.exe` and
`WindowsTerminal.exe` happen to be single-process, which is exactly why this
didn't show up in A18's own original testing.

**Fixed, not just documented as a known gap**: `_find_top_level_hwnds()`
(new) enumerates real top-level windows via `win32gui.EnumWindows`, filters
by visibility/title/owning-process-name via `psutil` (the same real
window-and-process approach this session's own benchmark-prep script had to
build first, now folded back into the actual production module), and
`resolve()` connects to each matching hwnd directly (`connect(handle=hwnd)`)
instead of trusting `connect(path=...)` to find the right process on its
own. Re-verified live against the same 33 targets after relaunching the
apps that had closed in the meantime:

| | Before fix | After fix |
|---|---|---|
| **UIA exact-name, overall** | 39.4% | **75.8%** |
| VS Code | 0% | 100% |
| Chrome | 0% | 66.7%* |
| Terminal | 83.3%† | 83.3% |
| Explorer | 100% | 100% |
| cortana's own control panel | 0%‡ | 0%‡ |

\* Two remaining Chrome misses are real page-state changes (the tab had
reloaded to a different exact title, and a transient search-suggestion pill
wasn't present), not a resolver failure.
† One miss was a benchmark-authoring slip (an automation ID recorded as if
it were an accessible name), not a system issue.
‡ Genuinely, structurally zero — Electron/Chromium content doesn't expose a
UI Automation tree without additional configuration cortana's own `ui/`
doesn't currently set. A real, different problem from the connect() bug,
not fixed this pass.

**This reframes Step 1's own result, per the explicit instruction to check
this before deciding how much the model swap matters.** UIA is exact where
it resolves — every target it recovers moves from probabilistic (a
grounding model's ~82% best case) to certain. Restricted to only the 8
targets across all 33 that the real (post-fix) UIA baseline still can't
reach, GTA1-7B and Holo2-8B are statistically tied — 6/8 (75%) each, with
different failure patterns (GTA1 misses both of cortana_ui's icon-only
window-chrome buttons; Holo2 misses the terminal tab title and cortana_ui's
minimize icon). The aggregate 30-point GTA1 lead across all 33 targets still
matters for apps/targets not in this benchmark or where UIA is structurally
unavailable (exactly cortana's own control panel today), but the UIA fix is
the bigger, cheaper win of this session — it made roughly two-thirds of the
previously-vision-dependent targets resolve with certainty instead of ~82%
confidence, for free, with no model download at all.

## The swap, applied

`[models].vision_grounding = "gta1-7b"` — a new, deliberately separate
config key from `[models].vision` (`gemma3:12b`, unchanged), not a
repurposing of it. `tools/cad.py`'s `_vision_check()` needs a
general-reasoning VLM for open-ended description/comparison ("does this
match, is anything misplaced") — exactly what `gemma3:12b` is validated for
(A14). GTA1-7B is the opposite: an RL-trained specialist whose own paper
describes rewarding successful clicks over verbose Chain-of-Thought
reasoning — correct for coordinate grounding, the wrong tool for CAD's
description task. Conflating the two under one key would have silently
handed the CAD vision check a model actively trained away from the kind of
reasoning it needs. `tools/computer.py`'s `_resolve()` and
`tools/_computer_vision.py`'s docstring both updated to read the new key and
reflect the real, current reasoning — re-verified end-to-end through the
actual production `_resolve()` function (not a standalone script) after the
change, on a real UIA-resolvable target.

## Step 2 — narrow arbitration, not always-run-both

**The overlap analysis that reframed this step's scope.** Before building
anything, checked the real surface Step 1's benchmark actually offers for
cross-validation: of the 33 targets, 25 had both UIA and the grounder fire.
Of those 25, 21 were the grounder merely agreeing with an already-exact UIA
answer, and the other 4 were the grounder being *wrong* — overruling a
correct answer with a worse one. So "both fire" is redundancy, not a useful
cross-validation surface, and PROMPTS.md's original framing (always run both,
require agreement within a tolerance) would add latency on every single
action for a benefit that measured out to roughly zero on this benchmark.

**Built narrower, on explicit instruction**: arbitration only fires when
UIA's own exact-name lookup misses *and* the miss is genuinely ambiguous —
one or more loose name matches exist — not on every action.
`tools/_computer_uia.py`'s `find_candidates()` (new) does the ambiguity
check: a permissive `difflib.SequenceMatcher`-based fuzzy match
(`fuzzy_match_threshold = 0.6`, `config/cortana.toml`) over every real UIA
element's accessible name, deliberately biased toward recall over precision
— a false positive here costs nothing (the model doing the picking just
ignores an irrelevant box), a false negative means a real candidate never
gets shown at all. Zero candidates falls through to the vision grounder as
pure last resort, unchanged from Step 1.

**Set-of-mark** (`tools/_computer_setofmark.py`, new): when candidates exist,
draws a numbered box over each one's *real* UIA rectangle on a screenshot of
the target window and asks a vision model to pick a number rather than emit
raw coordinates — removes coordinate hallucination as a failure mode
entirely, since every box is a real, tree-sourced rectangle and the model's
only job is picking an index. Uses `[models].vision` (`gemma3:12b`), not
`[models].vision_grounding` (`gta1-7b`) — this is a multiple-choice
reasoning task ("which of these N labeled regions matches this
description"), not raw-coordinate grounding, so it's the general-purpose
model's job per the same division of labor A22's Step 1 swap established.
A set-of-mark pick is UIA-exact on *location* but a guess on *which*
candidate was meant, so `tools/computer.py` requires confirmation
unconditionally for it, same as raw vision.

**Live-verified, not just unit-tested** — against a real Explorer window
(the one already-allowlisted app), read-only where possible:
- Exact resolve unaffected: `resolve('tools')` still finds the real `tools`
  ListItem directly, no candidate/set-of-mark path touched.
- **The realistic failure case set-of-mark exists for** — the one PROMPTS.md
  itself flagged as never having been exercised by Step 1's benchmark (every
  target there was searched by known-correct exact name, the easy case):
  `find_candidates('the config settings')` correctly surfaced the real
  `config` ListItem via fuzzy matching on a target that doesn't share an
  exact string with any accessible name, and `_computer_setofmark.resolve()`
  end-to-end (real screenshot, real numbered box drawn over the real rect,
  real `gemma3:12b` call) correctly picked it.
- A second descriptive probe, `find_candidates('documentation folder')`,
  surfaced `Documents (OneDrive)` from the sidebar — a plausible, real fuzzy
  match, confirming the candidate-gathering logic behaves sanely on a query
  with no single obvious match rather than returning nothing or garbage.

**Formal descriptive-target benchmark, VS Code + Chrome** (user's explicit
follow-up request — the two apps where set-of-mark actually matters most,
since Explorer's items mostly *do* have exact accessible names, so the probes
above were the easy version). 12 targets (6 per app), every one phrased
functionally/visually and deliberately avoiding the literal accessible-name
words (e.g. "the icon that starts debugging the code," never "Run and
Debug"). Ground truth taken from a live UIA enumeration of each app's real
window immediately before scoring, same discipline as Step 1's own benchmark.

**A real methodology problem found and fixed before the number could be
trusted at all**: the first two scoring passes came back wildly inconsistent
run to run (VS Code 0/6 → 2/6 with no code change in between; Chrome 5/6 →
0/6) purely from testing against whichever window happened to be topmost.
`find_candidates()` legitimately aggregates across *every* top-level window
matching a process name (correct, intended behavior for multi-window apps),
but the user has multiple Chrome windows/tabs open and in active concurrent
use — the topmost one changed mid-test-suite from a window titled "Instagram"
to one titled "The Fall Teenagers Can't Avoid - YouTube," and VS Code fully
exited and relaunched with a different restored file between runs. Fixed by
opening one dedicated, pinned Chrome window for the test and filtering
`find_candidates()`'s results down to that specific `hwnd` before scoring —
immune to what else the user's machine is doing. Reported here because
"testing against a live, actively-used machine gives non-reproducible
numbers unless you pin the target" is itself a real, generalizable finding
for any future live benchmark on this project, not just this one.

**Result, once reproducible: 8/12 targets recalled (the real element
surfaced as a candidate at all), 6/12 correct end-to-end (set-of-mark also
picked it).** Meaningfully lower than the initial unpinned spot-check
suggested — the honest number, not the flattering one. Three distinct
failure categories, not one:
1. **Candidate-recall misses from compound accessible names** — VS Code's
   "Source Control (Ctrl+Shift+G) - 3 pending changes" and "Run and Debug
   (Ctrl+Shift+D)" never surfaced as candidates for their descriptive
   targets. A real, separate bug was found and fixed along the way here:
   `_fuzzy_matches()` compared the *whole* accessible name against short
   target words via `SequenceMatcher.ratio()`, and VS Code's near-universal
   "(keybinding)" suffix measurably drags that ratio down — confirmed
   empirically, "extensions (ctrl+shift+x)" vs "extensions" scores 0.57,
   under the 0.6 threshold, on a name that's an exact semantic match. Fixed
   by stripping trailing parenthetical groups before matching
   (`_strip_trailing_parens()`, new). This closed some cases (Extensions,
   Toggle Panel) but not all — "- 3 pending changes" isn't parenthetical, and
   "debugging" vs "debug" isn't a strong enough fuzzy match on its own. Not
   chased further this pass, to avoid hand-tuning the matcher against this
   exact 12-phrase set rather than a real, generalizable pattern.
2. **Genuine set-of-mark picking errors on correct candidates** — Chrome's
   bookmark and extensions targets both had the real element in the
   candidate list, and `gemma3:12b` still picked wrong (`'All Bookmarks'`
   instead of `'Bookmark this tab'`) or declined to pick at all. A different
   failure class from (1): the mechanism worked, the model's judgment didn't.
3. **One structurally hard case** — "the icon that shows the signed-in
   user's profile" never recalled `'allen (stxtico)'`, a real, expected
   miss: a username has no semantic relationship at all to a functional
   description of what it visually represents. Name-based fuzzy matching
   can't solve this category; it would need a different approach entirely
   (position/role heuristics, or vision), out of scope for this pass.

### Is set-of-mark worth keeping? The comparison that actually answers it

6/12 alone has no baseline — it's meaningless without knowing what these 12
targets would score *without* set-of-mark, which is exactly what happens
today when it doesn't exist: they fall through to the pure GTA1-7B grounder
as last resort. Since all 12 were constructed to fail exact-name UIA lookup,
this is precisely the population set-of-mark exists to help, so it's the
right comparison, not a cherry-picked one. Ran the identical 12 targets,
same pinned windows, same ground truth (this time scored point-in-box, the
same methodology as Step 1's own ScreenSpot-style benchmark, since the pure
grounder has no candidate list to check recall against — just a coordinate).

| | VS Code | Chrome | Overall |
|---|---|---|---|
| **Set-of-mark** | 3/6 | 3/6 | **6/12** |
| **Pure GTA1-7B grounder** | 0/6 | 4/6 | **4/12** |

**Set-of-mark wins overall (6 vs 4), but the aggregate hides a real split
worth keeping, not flattening into one number.** On VS Code's dense,
small (36x36px), icon-heavy activity bar, set-of-mark won decisively —
0/6 for the pure grounder, which never once landed inside a 36px target on
that screen. On Chrome's larger, sparser toolbar, the pure grounder actually
*edged out* set-of-mark (4/6 vs 3/6) — and it got the one target set-of-mark
structurally cannot attempt: `"the icon that shows the signed-in user's
profile"` correctly landed inside `allen (stxtico)`'s rect, because vision
needs no accessible name to work from at all, exactly where name-based
fuzzy matching has zero signal. The two tiers have complementary failure
modes, not a strict ordering — set-of-mark's advantage concentrates where
targets are small and dense (name matching has an exact string to anchor
to; raw pixel-pointing doesn't), and it evaporates or reverses where a
target's real identity has no semantic relationship to its visual meaning.

**Verdict, per the standing decision rule**: set-of-mark wins the overall
comparison it needed to win to justify existing, so it stays, and the two
failure categories above (compound-name fuzzy-match misses, set-of-mark's
own picking errors on correctly-recalled candidates) are worth chasing —
not deleted as dead weight. Caveat honestly: n=6 per app is small, and the
Chrome result specifically suggests the current narrow-arbitration design
(fire set-of-mark whenever UIA is ambiguous, never falling back to the pure
grounder even when *it* might do better) isn't obviously optimal on sparser
UIs — a real, open question for a future pass, not resolved by this
comparison, just surfaced by it.

## Step 3 — verify actions instead of firing blind

**Mechanism** (`tools/_computer_verify.py`, new): `tools/computer.py`'s
`execute()` snapshots state immediately before every click/type and compares
against a fresh snapshot after (following a real, configurable settle delay
— `[tools.computer.verify].settle_delay_s = 0.4`, since re-checking
immediately would catch mid-animation UI states as false signals either
way). Which signal depends on how the target was resolved, not a single
universal check:
- `uia` / `uia_setofmark` (an accessibility-tree entry exists): re-query the
  tree for the same element by name and compare control type + rectangle.
- `vision` (no tree entry to re-check): diff a small screenshot region
  around the click point (`diff_radius = 60`px, `diff_threshold = 8.0` mean
  per-channel pixel difference — nonzero on purpose, since two real
  screenshots of a genuinely unchanged region still measure a small nonzero
  diff from PNG re-encoding and rendering noise).

**Neither signal is a pass/fail oracle**, deliberately — PROMPTS.md's own
framing for this step is "turn silent failures into caught ones," not
"auto-decide success," and an element resolving identically after a click
might mean the click had no effect *or* that its effect was elsewhere in the
window. Two things built in on top of the base mechanism, both from explicit
instruction:
- **Every verification outcome is logged with the tier that produced the
  target** (`resolved_via`) alongside the verification tier and outcome
  (`logs/computer.jsonl`'s `verify_tier`/`verify_outcome` fields) —
  specifically so a pattern of UIA-resolved actions failing their post-check
  would actually become visible later. Before this, a wrong UIA element
  resolved and clicked with exactly the same confidence as a right one, and
  nothing existed to surface the difference.
- **On a mismatch, no automatic retry.** The verification detail is appended
  to what `execute()` returns (`"Verification (uia): 'config' resolves
  identically... no UIA-visible state change detected."`) so a human or the
  calling agent decides what to do next, not this module guessing at a
  crop-and-retry loop.

**Live-verified, read-only**: ran a full snapshot → compare cycle against a
real UIA element (`tools`) in Explorer with *no action in between* —
correctly reported `unchanged`, confirming the comparison logic itself is
sound (same-state input produces the same-state verdict, not a false
positive from re-querying volatility alone). Also fixed a real, separate
bug found while wiring this in: `tools/_computer_vision.py`'s `resolve()`
signature had already been rewritten (uncommitted, from before this
session's context was reopened) to the two-stage `(grounding_model,
description_model, description, hwnd)` shape, but `tools/computer.py`'s
`_resolve()` was still calling it with the old two-argument shape — the
pure-vision fallback tier was silently broken (would `TypeError` on the
first call) until this pass. Re-verified live after the fix: a real
`gta1-7b` grounding call + real `gemma3:12b` description call against a live
desktop screenshot, returned a valid coordinate + description string.

**Live-tested end-to-end, on explicit request**: two real actions through
`execute()`'s full path (resolve → walk → cursor → click → verify) against a
real Explorer window, specifically chosen to exercise both verdicts, not
just prove the mechanism runs:
- **Double-clicking a folder ("tools") to open it** - a genuine, visible
  state change. Returned: `"Verification (uia): 'tools''s accessibility-tree
  state (control type or rectangle) changed after the action."` Correctly
  reported `changed`, not a false `unchanged` - the comparison isn't too
  narrow to notice a real change (re-resolving "tools" after navigating into
  it found either a different element or none at the same identity, either
  way a real UIA-visible difference).
- **Single-clicking a different folder ("docs") in a fresh window** - a
  harmless no-op at the tree-state signal level (selection changes, but the
  clicked element's own control type and rectangle don't). Returned:
  `"Verification (uia): 'docs' resolves identically (same control type and
  rectangle) before and after the action - no UIA-visible state change
  detected."` Correctly reported `unchanged`.

Both verdicts are reachable on real actions, not just in the isolated
before/after comparison test run during the initial build - confirms the
mechanism actually discriminates rather than defaulting to one answer.

## Not done yet

Step 4 (read-only screen awareness) is still ahead. Both items previously
listed here (a formal descriptive-target benchmark for Step 2, a live
full-click verification pass for Step 3) are now done - see above for
results. What the benchmark itself surfaced as still open: the two
un-chased fuzzy-match failure categories (compound accessible names like
"- N pending changes" suffixes, and near-but-not-quite word matches like
"debugging" vs "debug"), and the set-of-mark model-picking error rate on
correctly-recalled candidates (2 of 8 recalled targets still picked wrong) -
both real, measured gaps, not yet worth a matcher-tuning pass against one
12-target set, but worth tracking if a larger test set someday confirms
they're systematic rather than incidental to these specific phrasings.
