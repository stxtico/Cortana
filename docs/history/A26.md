# A26 — FreeCAD scripting

A `freecad` tool that sends Python to an already-running FreeCAD GUI instance via a small,
self-owned XML-RPC bridge, reusing A14's geometric validation and export path unchanged.
FreeCAD isn't installed on this machine - built real and self-gating, same "OCR before
Tesseract landed" precedent, with everything genuinely testable actually verified.

## The transport decision, stated plainly (asked for explicitly)

FreeCAD exposes three real paths for external control:

1. **A console command file.** FreeCAD doesn't watch a directory and auto-execute a macro
   dropped into it. Nothing about writing a file makes an *already-open* GUI instance run it
   without a second, separate trigger - a human clicking Execute, or driving that menu via
   UIA, which reopens exactly the GUI-automation fragility PLAN.md's "GUI question" section
   built this whole feature to avoid in the first place.
2. **`import FreeCAD` from an external process** - this project's own venv could do this in
   principle, the same way `scripts/_cad_common.py`'s headless generation already works. It
   creates its own, separate, disconnected in-memory FreeCAD session. It never touches
   whatever the user actually has open. Wrong tool for "renders live where I can rotate it" -
   the literal, stated point of this feature.
3. **A socket/RPC server, started from inside the already-running GUI process.** The only one
   of the three that actually satisfies "an already-running instance executes code and shows
   the result live."

Picked (3). Built as a small, fully self-owned XML-RPC bridge
(`scripts/freecad_rpc_bootstrap.py`, ~60 lines of stdlib) rather than depending on a
third-party FreeCAD RPC addon - unverifiable without installing FreeCAD to check, unclear
current maintenance status, and this project's own established pattern (A23's `media_control`
writing its own temp `.ps1` script rather than depending on someone else's automation bridge)
is to own small, fully-understood transport code end to end.

**What it can't do, stated plainly (also asked for explicitly):**
- Doesn't survive closing FreeCAD - it's a live bridge into a live process, not a service. The
  user re-runs the bootstrap script after every fresh FreeCAD launch.
- Localhost only, never `0.0.0.0` - nothing outside this machine can reach it. Still real
  capability worth knowing is active: arbitrary Python execution inside a GUI process.
- FreeCAD's GUI (Qt) isn't thread-safe from arbitrary background threads - the XML-RPC
  server's own listener thread can't safely call `FreeCADGui`/3D-view functions directly.
  Handled with a `QTimer`-polled queue that marshals every `run_code()` call onto FreeCAD's
  own main/GUI thread (50ms poll) - a real fix for a real constraint, not decoration. Tries
  `PySide6` then `PySide2` then `PySide`, since which one FreeCAD bundles changed across major
  versions (0.20/0.21 vs 1.0+).

## Reused, not reimplemented

`render_part` loads an already-generated, already-verified part into the live FreeCAD document
via FreeCAD's own built-in STEP importer (`Part.insert()`) - not regenerated through FreeCAD's
native Part/Sketcher API. That would be a second geometry-generation path for the same part,
which could diverge from what `verify_solid()` (A14) actually measured - "same solid, same
checks" means the exact CadQuery-built, already-verified solid is what appears in FreeCAD, a
display bridge, not a second modeler. STEP lookup/export reuses
`tools/_cad_export_common.py`'s `find_part_script()`/`build_default_solid()` - the exact code
`export_step.py` already uses, not a second implementation. If a part's STEP hasn't been
exported yet, `freecad.py` exports it the same way `export_step.py` would before sending it.

## Confirmation gating, split by action

`render_part` (load an already-verified file into a document) needs no confirmation - no more
consequential than `export_step.py`'s own unconfirmed write. `run_python` (arbitrary code
execution inside a live GUI process) is confirmation-gated like `tools/shell.py` -
`REQUIRES_CONFIRMATION = False` at module level, `execute()` calls `agent_safety.confirm()`
conditionally, same per-action pattern `tools/computer.py` already established in A18/A25.

## Verified everything genuinely testable without FreeCAD installed

FreeCAD isn't installed on this machine (checked live: no `FreeCAD.exe`, `winget` finds
nothing under that ID locally either). Per explicit instruction, built real and self-gating
rather than skipped, with the gap stated plainly rather than glossed over.

What **was** verified, live, this session:
- A real stand-in XML-RPC server (plain Python, same `ping()`/`run_code()` protocol shape as
  the bootstrap script, on the same configured `localhost:9875`) exercised the actual,
  registered `tools/freecad.py` end to end - `is_available()`, both actions, confirmation
  gating, and error propagation.
- **A real bug found and fixed by this same test.** `_render_snippet()`'s first draft opened
  with `import FreeCAD, Part` - but `run_code()` (both the bootstrap script and the stand-in)
  already `exec()`s every sent snippet against a namespace pre-seeded with
  `FreeCAD`/`FreeCADGui`/`Part`, so an explicit import was redundant at best and, in the
  stand-in test, broke outright (`ModuleNotFoundError: No module named 'FreeCAD'` - the fake
  namespace seeding doesn't intercept a real `import` statement, only bare-name lookups).
  Fixed by removing the import and relying on the documented pre-seeded namespace contract
  instead - a cleaner design than the one that broke, not a workaround for the test.
- `render_part` against the real, already-verified `cad/verified/bracket` part: the fake
  `FreeCAD`/`Part`/`FreeCADGui` stand-in recorded the actual calls the generated snippet made
  (`newDocument('cortana_bracket')`, `Part.insert(<real step path>, ...)`,
  `doc.recompute()`, the view-fit sequence) - not just "the snippet parses," genuine behavioral
  verification against a stand-in with real enough semantics to catch the import bug above.
  Then, external to the tool's own return: re-imported the resulting `bracket.step` with
  cadquery's own STEP importer (a completely separate code path from the one that wrote it)
  and confirmed it's a real solid with positive volume, not a corrupt or empty file.
- 10/10 checks passed.

**What genuinely could not be verified, stated plainly:** `scripts/freecad_rpc_bootstrap.py`'s
own FreeCAD-specific calls - `Part.insert()`'s real behavior, `FreeCADGui.activeView()`,
whether the QTimer/PySide threading marshaling actually works inside a real FreeCAD process.
This is a best-effort first draft against documented FreeCAD API behavior and well-known Qt
threading constraints, not a live-verified one. The user installs FreeCAD and reports back
what breaks - same honesty standard A24 held OCR to before Tesseract was installed.

## Setup, when the user is ready

```
winget install --id FreeCAD.FreeCAD
```

Then, with FreeCAD open: **View > Panels > Python console**, paste in
`scripts/freecad_rpc_bootstrap.py`'s contents (or run it as a macro). Once per FreeCAD
session - it doesn't persist across closing FreeCAD. `is_available()` checks this live (a real
`ping()`, not just "is FreeCAD.exe running") - `freecad` stays dormant, correctly, until both
steps are done.
