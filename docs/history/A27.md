# A27 — Crawl4AI

`fetch_url` gains a config-selectable backend: trafilatura (unchanged, still default-first),
Crawl4AI (a real headless browser, for pages whose content is rendered client-side), and
`auto` (trafilatura first, Crawl4AI only as a fallback when the result is empty or
suspiciously short) - the default, decided by measurement, not assumption, per explicit
instruction.

## Measured, on real pages, before picking a default

**Static pages (both extract correctly - "tells you nothing" about which is better for JS
content, PROMPTS.md's own framing, included as a no-regression baseline):**

| Page | trafilatura | Crawl4AI |
|---|---|---|
| quotes.toscrape.com (static) | 0.97s, 1654 chars | 4.09s (cold start), 4322 chars |
| Wikipedia: Web scraping | 0.23s, 26999 chars | 0.97s (warm), 71679 chars |

Both backends got the real content in both cases. trafilatura was faster **and** cleaner in
both - Crawl4AI's markdown (even with `fit_markdown`'s `PruningContentFilter` applied)
included more boilerplate than trafilatura's extraction ever did.

**The case that actually matters - content rendered client-side:**

| Page | trafilatura | Crawl4AI |
|---|---|---|
| quotes.toscrape.com/js/ | 0.11s, **29 chars** (the loading shell: "Quotes to Scrape / Login / Next") | 1.02s (warm), 1663 chars, the real quote content |

trafilatura didn't just do worse here - it returned something that reads as a successful
fetch (a 200, non-empty text) while missing the actual content entirely. Crawl4AI got it
right, at several times trafilatura's typical latency (as anticipated: "several seconds
versus a few hundred milliseconds" was the actual measured shape, not a specific number
picked in advance).

## The decision

`auto` (default): trafilatura first, Crawl4AI only when trafilatura's result is under
`auto_fallback_min_chars` (200, config-driven). Reasoning, directly from the numbers above:
trafilatura is strictly better whenever it actually works (faster, cleaner), and a genuinely
thin/empty trafilatura result is itself the signal that a page needs real JS rendering - so
the fallback fires exactly where it's needed, without paying browser cost speculatively on
the large majority of pages that don't need it. `trafilatura` and `crawl4ai` remain available
as explicit, unconditional overrides (`[tools.fetch_url].backend`).

`tools/_crawl4ai.py` launches a fresh `AsyncWebCrawler` (and fresh browser) per call rather
than holding one open across the process lifetime - a deliberate departure from CLAUDE.md
rule 7's usual "one persistent instance" guidance, since a standing browser process is real
resource cost for a tool called occasionally, not every turn; the measured per-call launch
cost (a few hundred ms to ~1s once past the very first cold start) is the right tradeoff here.

`logs/fetch_url.jsonl` (new) records `backend_used` and character counts on every call,
including whether a fallback was attempted and its outcome - the same "instrument before you
optimize" discipline (CLAUDE.md rule 3) A25's `computer_stats.py` already established for
`tools/computer.py`, so a real-world backend-selection pattern is visible later if it ever
needs revisiting, not just asserted here.

## Live-tested against the real, registered tool - verified externally

Per explicit instruction ("a fetch that returns 200 with an empty body reads as success" -
exactly what happened above with trafilatura on the JS page): checked the real
`tools/fetch_url.py`'s `execute()`, not the standalone comparison script, against known,
real page content rather than "is it non-empty."

- Static page: extracted text contains the real, known quote text; log confirms
  `backend_used: "trafilatura"`, no fallback attempted.
- JS-rendered page: extracted text contains the real, known quote text (not the loading
  shell); log confirms `backend_used: "crawl4ai"` with `fallback_from_trafilatura_chars: 29`,
  proving the fallback genuinely fired and genuinely helped, not just that both backends
  happened to return non-empty text independently.

5/5 checks passed.
