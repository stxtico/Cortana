- **A21 - Delegation (`services/workers/`).** Shaped like `services/daemon/`
  per explicit instruction: `queue.py` (a JSON-backed durable task list,
  main-process-owned) plus `status.py` (one atomically-written status file
  per task, worker-owned) - the fourth instance of this project's
  established Python<->cross-process atomic tmp+rename+retry pattern
  (`playback_state.py`, `listening_state.py`, `walk_signal.py`), not a new
  mechanism, following the same "single-writer-per-file, split both ways"
  discipline `walk_signal.py`'s own docstring already established rather
  than one file two processes both write to.
  **Workers are processes, not model instances - genuinely no second model
  resident**, confirmed by measurement, not assumed: every worker is a real
  OS subprocess making calls to the exact same already-running Ollama
  server the conversation loop uses, same reasoning `daemon.py`'s own
  docstring already gave for why that process can coexist. Two worker
  kinds, config-driven per `[workers.types.<name>]`:
  `kind="script"` wraps an existing standalone module as a subprocess with
  CLI args (`services.marketing.pipeline` - genuinely unmodified, "already
  runs standalone" held completely true, zero changes needed there) and
  never touches `agent.py`'s tool dispatcher at all, so "inherit the
  parent's gates" is trivially satisfied - there's nothing gated to reach.
  `kind="agent"` (the `cad` worker: `cad_generate`/`export_step`/
  `export_stl`/`read_file`/`list_dir`/`find_file`/`write_file`) runs a new
  subprocess entry point, `worker_main.py`, which calls `agent.py`'s real
  `run_agent()` - extended with one new optional parameter,
  `tool_names`, that bypasses the existing by-model lookup and scopes to an
  explicit list instead. "Specialization is the tool set, not the model,"
  literally: the exact same dispatcher, the exact same `_call_tool()`
  gates, just a smaller `tools` dict.
  **Rails, verified live, not just written:**
  - *Worker output is data, never instruction* - a worker's status/result
    text returns from `task_status` as an ordinary tool-result string, the
    same boundary `fetch_url`'s page content already crosses; nothing
    downstream re-parses it as a command. No new code needed here - this is
    the same convention every existing tool result already follows.
  - *Workers inherit the parent's gates exactly, enforced per-tool at the
    dispatcher* - verified two ways. Structurally: filtering `_ALL_TOOLS` by
    the `cad` worker's configured `tool_names` confirmed zero leakage of
    `shell`/`computer`/`web_search`/`delegate_task`/etc. Live: ran a real
    `cad`-kind worker subprocess with a task designed to trigger
    `write_file`'s `REQUIRES_CONFIRMATION` gate. This surfaced a real bug
    before it could ever bite in production - `agent_safety.confirm()`'s
    `input()` call raises `EOFError` immediately on a worker's `stdin=
    DEVNULL` (deliberate, so a worker can never consume input meant for a
    foreground prompt - the same bug class A10 already hit once with
    `tools/shell.py`'s `_run_wsl()`), and the pre-existing `confirm()` only
    caught `TimeoutError` - an uncaught `EOFError` would have crashed
    `run_agent()`'s whole loop instead of just failing the one gate closed.
    Fixed by catching `EOFError` identically to a timeout (declined, logged,
    no crash) before ever testing it. Re-ran live: `logs/agent.jsonl` showed
    `{"stage": "confirmation", "outcome": "no_stdin"}` followed by the
    `write_file` call itself logged `"ok": false` - the worker completed
    gracefully reporting the decline, and the target file was confirmed
    never created.
  - *Hard concurrency cap from config, default 2* - verified live: spawned
    3 real marketing tasks at once, confirmed exactly 2 real subprocesses
    ever ran concurrently (`len(manager._active) == 2`, not 3), the third
    sat `queued` with no process behind it, then genuinely started the
    instant one of the first two finished ("a task queue... and workers
    that pull it off," literally - a worker finishing is what triggers the
    next one starting, no separate poll loop).
  - *The kill switch must stop every worker, not just the foreground task* -
    the rail given the most explicit weight, tested accordingly. Every
    spawned worker registers a live `Process` handle with
    `agent_safety.py` the instant it starts; `_on_abort_hotkey()` was
    extended to terminate every tracked worker alongside cancelling the
    foreground task (`Process.terminate()` is a direct OS call with no
    event-loop dependency, confirmed safe to call straight from the
    keyboard hook's own thread - verified empirically rather than assumed,
    this codebase has been burned by exactly that kind of unverified
    cross-thread assumption before, A18's `keyboard.send()`/
    `SetForegroundWindow` surprises). Live test: spawned 2 real workers with
    real OS PIDs, registered a fake foreground task alongside them, called
    the real abort-hotkey callback. Result: foreground task received a real
    `CancelledError`, both workers' PIDs confirmed **gone from Windows'
    actual process list** via `tasklist` - not just our own bookkeeping,
    independent OS-level proof. A genuinely different code path from the
    single-task cancel A18 already verified, now itself verified the same
    rigorous way.
  - *One tool call over a sequence she has to reason through correctly* -
    the A18 finding (`find_file`: 2/3 -> 3/3 by collapsing a multi-step
    chain into one call) applied deliberately here, not just cited:
    `task_status()` called with no `task_id` returns every task's state in
    one string (`manager.format_all()`), so "manage several workers" is one
    call, not a loop she'd have to run and get right every time.
  **`worker_trigger.py`** (`services/daemon/`) makes the A21 done-when real:
  polls the same status files, matching `timers.py`'s exact
  `is_available()`/`poll()` interface, wired into `daemon.py`'s existing
  `_SOURCES` list with zero changes to that file's own poll/relevance/
  quiet-hours/rate-limit machinery. Verified live: after a real marketing
  worker completed, `worker_trigger.poll()` returned a real "Your marketing
  task just finished" candidate carrying the worker's actual printed
  report as detail - the exact mechanism that lets the daemon announce it
  through the existing pipeline.
  **Known, minor, honestly-stated gap**: a worker terminated via the global
  abort hotkey currently reports as `failed` ("exited with code 1") rather
  than a more specific "aborted via kill switch" label - the stop itself is
  real and rigorously verified, only the status record's stated *reason*
  is generic. Not fixed this pass - would need `agent_safety.py` (a
  foundational safety module) to signal back into `services/workers/`
  specifically, which felt like the wrong layering to add for a cosmetic
  label given everything else this session prioritized real verification
  over polish.
  **Done-when verified for real, matching PROMPTS.md's exact wording**: "you
  ask for a batch, she starts it, you have a normal conversation while it
  runs, and she tells you when it's done" - `delegate_task` returned in
  ~20ms, three simulated conversation turns ran while the real render was
  in progress, `task_status()` showed live progress, the task genuinely
  completed with a real result, and `worker_trigger` surfaced the real
  completion for the daemon to announce.
