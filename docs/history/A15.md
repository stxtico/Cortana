# A15 — The character (Live2D placeholder rig)

Moved verbatim from CLAUDE.md's Done log (2026-08-12 restructure) — see

- **A15 — The character (`ui/character.html`, `ui/src/character_*.ts`), a
  second Electron window alongside A12's control panel, not a separate app.**
  Live2D placeholder rig: "Shizuku," Live2D's own free Cubism 2.1 SDK sample
  character, fetched via a real, reproducible script
  (`scripts/fetch_live2d_placeholder.py`, 33 files - moc, 4 expressions, 18
  motions, 6 textures, physics/pose data) mirrored in `pixi-live2d-display`'s
  own test suite rather than a manual download - gitignored
  (`ui/assets/live2d/`), same "third-party content we use locally but don't
  redistribute through git" reasoning as `voice_source/`.
  **Real dependency friction, checked and resolved before building, same
  discipline as every prior integration**: `pixi-live2d-display@0.4.0`
  (latest non-beta) lists `gh-pages` as a production dependency by mistake
  upstream (a doc-deployment tool with zero business being a runtime
  dependency) - flagged critical by `npm audit`. `0.5.0-beta` fixes the
  packaging but requires PixiJS 7 (a bigger, riskier jump for a beta-of-beta
  combination). Landed on `0.4.0-beta.2` - same Pixi 6.x target as stable,
  empty `dependencies`, zero `npm audit` findings. No bundler in `ui/` (A12's
  split-tsconfig precedent already established this) - PIXI, the Cubism 2
  core runtime, and the Live2D bundle all load as plain global-namespace
  `<script>` tags referencing `node_modules/` directly, same as most Live2D
  web tutorials use them without a build step.
  **Window mechanics, verified against the real OS, not just "the code looks
  right"**: `transparent: true` + `frame: false` + `alwaysOnTop` +
  `skipTaskbar` + `setIgnoreMouseEvents(true, {forward: true})` by default.
  Real screen capture (not `webContents.capturePage()`, which can't see
  OS-level window compositing at all - confirmed by A12's `window_opacity`
  investigation) showed real desktop content correctly bleeding through
  around her, proving genuine transparency, not an approximation.
  **Gaze tracking (explicit priority - "do this one early") uses the real
  global cursor, not a local-hover proxy**: `screen.getCursorScreenPoint()`
  polled from the main process at ~30fps, since that works regardless of
  focus or click-through state (the renderer alone can't see the cursor at
  all when it's outside the window). Verified with real mouse movement to
  extreme positions, including the *other monitor* entirely - two screenshots
  showed genuinely different head/eye angles between far-left and far-right
  cursor placement, confirmed via `model.focus(x, y)`
  (`pixi-live2d-display`'s own built-in focus API, not hand-rolled bone
  manipulation).
  **Multi-monitor walking verified with real window-position tracking across
  two real 2560x1440 displays** (confirmed attached via
  `System.Windows.Forms.Screen.AllScreens` before trusting any of this could
  be tested for real). PLAN.md's specific instruction - walk off the near
  edge, jump instantly to the target display's corresponding edge ("sell the
  \[bezel] gap... rather than trying to render continuous motion"), walk on
  from there - implemented as a three-phase `animateX()` sequence in
  `character_main.ts`. Triggered via a real global hotkey (`Alt+Shift+W`,
  Electron's `globalShortcut`, cycles to the next display) since deciding
  *when* to walk (following the active window, reacting to a call) is a real
  backend-integration step this doesn't attempt - same "mechanism built,
  live-trigger wiring deferred" pattern as every other tool integration in
  this project. Verified via `GetWindowRect` before/mid/after a real
  triggered walk: window X position moved from the primary display's
  coordinate range (0-2560) to the secondary's (-2560-0), confirmed
  numerically and with a real screenshot showing her on the second monitor
  over different real desktop content. Hot-plug safety
  (`display-added`/`display-removed`/`display-metrics-changed` →
  reposition to primary if off-screen) built the same way but not
  physically tested (would need actually unplugging a monitor) - the check
  itself directly reuses the same real-display-bounds logic already proven
  live for the walk.
  **State machine and emotion overlay are a real, working mechanism with an
  honestly-stated limitation**: Shizuku's free rig has exactly one real
  motion group ("idle," 3 variants) and no state-specific animations of its
  own - not a claim this placeholder doesn't actually support, stated
  plainly in `character_renderer.ts`'s comments. All six states
  (idle/listening/thinking/speaking/walking/working) differentiate via which
  of the rig's four expressions is active, layered independently of the
  motion - the actual "emotion as a separate overlay" architecture PLAN.md
  asked for, verified with three real screenshots showing genuinely distinct
  expressions (listening: narrowed/attentive; thinking: drawn-together
  brows; speaking: a real smile) per state. A commissioned rig would give
  each state its own motion; this one doesn't, and the code says so.
  **Lip sync required a real Python-side extension and surfaced two real
  bugs, not one.** `services/voice/playback_state.py` (A11's existing
  cross-process signal file) gained `update_amplitude()`, called from
  `tts.py`'s `_write_interruptible()` - the one shared playback primitive
  both `play_audio()` (backchannels) and `_play_all()` (real responses)
  already go through, so both drive the mouth for free. Bug 1: `play_audio()`
  never called `mark_stopped()`, so a backchannel's last sub-block amplitude
  would stick after playback actually ended instead of the mouth closing -
  fixed with a `finally`-block reset inside the one shared primitive, not
  duplicated per caller. Bug 2, more serious, found via real ticker-level
  logging while chasing what looked like a silent failure: a genuine Windows
  file-locking race - `ui/`'s frequent reads of `playback_state.json`
  (`fs.watch` plus a backstop poll) could collide with Python's atomic
  `os.replace()`, which (unlike POSIX rename) requires exclusive access to
  the destination on Windows, raising `PermissionError`. That exception was
  **not** caught anywhere in `_write_interruptible`'s hot loop - live, this
  would have crashed real audio playback mid-sentence, a far worse outcome
  than dropping one amplitude update. Fixed with a tolerant retry-then-
  drop-and-log inside `playback_state.py`'s `_write()` itself, covering every
  caller (`mark_started`/`mark_stopped`/`update_amplitude`) at the one real
  chokepoint. Separately, a one-shot `setParamFloat()` per amplitude update
  turned out not to work at all - the rig's own idle motion animates the
  same mouth parameter as part of its breathing/talking-idle curve, silently
  overwriting a one-shot set on the very next frame. Fixed by reapplying the
  current amplitude every tick via `app.ticker` (registered after the
  model's own update callback, so it wins each frame) instead of on receipt
  - confirmed correct with real frame-by-frame logging showing the Cubism
  parameter tracking the amplitude value exactly, transition for transition,
  across a real oscillating test sequence.
  **A real, unrelated-looking bug turned out to be a false alarm from
  unreliable tooling, not a regression** - worth recording so it isn't
  rediscovered the hard way again: with both windows running,
  `Get-Process | Select MainWindowTitle` reported only the character window,
  making the control panel look like it had silently failed to appear.
  Added explicit `ready-to-show`/`did-finish-load` tracing and confirmed
  every lifecycle event fired correctly with no exceptions anywhere -  the
  control panel genuinely was rendering the whole time. A real full-desktop
  screenshot (not the process-title heuristic) settled it: both windows
  visible simultaneously, control panel included. `Get-Process`'s
  `MainWindowTitle` is simply unreliable once more than one Electron
  `BrowserWindow` exists in the same app - noted here so the next
  multi-window debugging session doesn't retread this.
  **Done-when, verified for real across all three parts**: launched via the
  real `npm start` entry point, confirmed on the real desktop via full
  screen capture that she's genuinely on screen (real transparency, not an
  approximation); confirmed real cursor tracking across extreme positions
  including the other monitor; confirmed a real triggered walk moved her
  window from the primary display's coordinate space to the secondary's,
  visually confirmed on the second monitor.
