# A18 — Computer use

Moved verbatim from CLAUDE.md's Done log (2026-08-12 restructure) — see

- **A18 - Computer use (`tools/computer.py`), built out of PROMPTS.md's
  numbered order per explicit instruction - highest-risk phase in the build,
  done deliberately once every other confirmation gate (A9) was already
  proven.**
  **Kill switch built and verified before a single click existed, exactly as
  instructed - three separate real tests, not one.** Reuses A9's existing
  `ctrl+shift+x` abort hotkey/task-cancellation mechanism rather than a
  second system - the real work was making `tools/_computer_input.py`'s
  eased cursor-move a genuinely cooperative async loop (many small steps,
  `await asyncio.sleep()` between each) so `asyncio.Task.cancel()` can land
  mid-motion, not just between tool calls. (1) Automated test
  (`scripts/computer_killswitch_test.py`): found `keyboard.send()` can't
  trigger `keyboard.add_hotkey()` at all (it sets an internal
  `is_replaying` flag its own hook checks and ignores), and a first raw
  `win32api.keybd_event()` attempt also silently failed - needed a real
  resolved scan code via `MapVirtualKey()`, not a bare virtual-key code,
  before the hook could match it. Fixed, then verified: cancelled at 1.13s
  against a 4.0s sweep, cursor stopped mid-path, a follow-up sweep completed
  clean (no stuck button state). (2) Real physical keypress from the user's
  own keyboard via `--manual` mode, added specifically because synthetic and
  physical events had just been shown not to be equivalent by default in
  this stack - confirmed working. (3) Focus-independence - same physical
  test with a browser/editor focused instead of the terminal, since real
  usage means the hotkey has to work while she's clicking in some other app,
  not this one - confirmed working. Along the way, `_on_abort_hotkey()` in
  `services/brain/agent_safety.py` was fixed to log every detection
  unconditionally, including a press with nothing registered - previously
  silently swallowed, so a genuine hook failure and a merely mistimed press
  looked identical from outside the process.
  **Four resolution tiers, priority order, per A14's own vision finding**:
  UI Automation (`tools/_computer_uia.py`, `pywinauto` backend="uia") first,
  Playwright (`tools/_computer_playwright.py`, browsers only, real code but
  `is_available()`-gated dormant on finding a CDP-attachable Chrome -
  attaching to the user's actual authenticated browser profile is the
  broadest capability in this whole build and was explicitly deferred as its
  own future decision, not bundled into this pass) second, a config-declared
  CLI recipe (`tools/_computer_cli.py`, never a shell string - same no-shell-
  string-ever argv discipline as `tools/shell.py`) third, vision +
  coordinates (`tools/_computer_vision.py`, `[models].vision`) only as
  absolute last resort - A14 found this exact model fabricates specific
  wrong claims about an image rather than admitting uncertainty, and
  separately produced a real false negative even in an already-hardened
  setup, so pixel-coordinate clicking driven by a model that invents details
  is the worst combination available here.
  **Performance layer built honestly, not approximated**: character walks
  horizontally toward the target (`ui/src/character_main.ts`'s new exported
  `walkToward()`, built from A15's existing `animateX` - no second movement
  system) - horizontal-only by explicit decision, since a character walking
  a plane reads as physically present and floating vertically to hover near
  a target would trade that for precision the eased cursor path already
  provides. **No fake reach gesture** - Shizuku's rig has exactly one real
  motion group and four expressions (A15), nothing that could represent
  reaching, so the sequence is walk -> the already-existing, already-honest
  `working` state -> the real eased cursor move
  (`tools/_computer_input.py`) -> brief pause -> click -> idle, not an
  invented animation the rig can't do. Python talks to the Electron
  character window through a new file-signal pair
  (`services/character/walk_signal.py`, `logs/computer_walk_request.json`/
  `computer_walk_status.json`), same atomic-write-with-retry pattern as
  `playback_state.py`/`listening_state.py` and the same standing decision
  against a new IPC transport (`ui/src/main.ts`'s own header comment) - not
  a new mechanism, the third instance of an established one.
  **Confirmation, allowlist, and password rules are all real dispatcher-
  adjacent code, not persona instructions** (CLAUDE.md rule 4).
  `REQUIRES_CONFIRMATION` is `False` at module level (the instruction was
  confirmation for send/delete/purchase/submit, not every click) -
  `execute()` calls `agent_safety.confirm()` directly and conditionally
  instead, still the same real gate the model can't route around, just
  invoked from inside the tool. Per-app allowlist
  (`[tools.computer.apps]`) is enforced twice: the `app` parameter's
  JSON-schema `enum` means the model structurally cannot name an
  unconfigured app (constrain the shape, don't filter content - same
  reasoning as `tools/shell.py`'s command whitelist, since A11's supposed
  "label validation" precedent turned out not to exist on inspection - the
  real citation is A14's `tools/_cad_units.py`), and the real foreground
  process is re-checked live immediately before every click/type, not
  cached from resolution time. Typing is only permitted when the target
  was resolved via UI Automation (where `CurrentIsPassword` is a real,
  structural property to check) - a deliberately narrower scope than
  "detect passwords everywhere," and a password-flagged field refuses
  unconditionally, no confirmation offered, since the instruction was
  "never," not "confirm first."
  **Vision fired live on the very first real attempt, and was wrong -
  caught cleanly by the mandatory confirmation gate, not by luck.** During
  end-to-end testing, a resolution miss on Explorer (see below) fell
  through all the way to vision, which claimed with specific confidence
  that it saw "the string 'cortana.toml' visible in a list of files within
  the VS Code file explorer window" - a real screenshot of the real desktop,
  misread as a completely different application than the one actually being
  driven. Because vision-resolved clicks require confirmation
  unconditionally (a deliberate addition beyond the four named action
  categories, made explicit with the user during this build - the *target*
  is unreliably identified there, not just the action), nothing fired
  blind: the confirmation prompt stated plainly that the target was
  vision-resolved and named exactly what it believed it was looking at, so
  the misidentification was visible before anything could be clicked. This
  is the strongest evidence yet for keeping that gate unconditional rather
  than narrowing it to the same four categories everything else uses.
  **Two real bugs found live during end-to-end testing, both fixed, neither
  worked around:**
  1. `explorer.exe` (and other GUI-launching Windows commands) routinely
     exits non-zero even on genuine success - it hands the request off to
     the already-running shell process; its own launcher exit code isn't a
     meaningful signal. `action="open"` was wrongly treating this as
     failure. Fixed to treat the exit code as informational for this
     action type, not pass/fail.
  2. The real reason UI Automation missed a real file inside a real,
     currently-open Explorer window: `pywinauto`'s `.descendants()` issues
     one `FindAll(TreeScope.Descendants)` from the top-level window, which
     does not reach Explorer's virtualized "Items View" list contents at
     all - it found the list container but zero items underneath. Calling
     `.children()` directly on that same list element returned the real
     items immediately (confirmed live: `models`, `cortana`, `persona`,
     `profile` - actual folder/file names, `cortana.toml` surfaced as
     `cortana` since this system hides known extensions by default). Not a
     hostile, unwalkable control - just needed realization triggered at
     each level via a manual recursive `.children()` walk
     (`tools/_computer_uia.py`'s new `_walk()`) instead of one distant
     top-down query, plus extension-tolerant name matching. Verified fixed
     against the same real window: `cortana.toml` now resolves to a real
     `ListItem` with a real center point.
  **One investigation that turned out to be a false alarm, corrected
  rather than left standing**: a prior session's finding that `cad/`
  "doesn't exist" was wrong - caused by checking from `ui/` (cwd had
  drifted there from an earlier `npm run build` and never returned to
  root), not a real repository problem. `git log`, `git ls-tree`, and
  `git cat-file` against `HEAD` all confirm `cad/verified/bracket/`'s four
  files were genuinely committed in A13 (`2d2406b`), remain in `HEAD`'s
  tree, and are present on disk right now - A13's pipeline did accumulate
  real training data as intended; nothing was lost. Recorded here so the
  false alarm doesn't get rediscovered the same way twice.
  **Resolved in a follow-up session, not left as a deferral**: a human-attended
  single-command test (`scripts/computer_e2e_test.py`, wired through the same
  `register_current_task`/`clear_current_task` the real dispatcher uses so the
  real abort hotkey works against it) ran the full walk -> cursor -> click
  chain start-to-finish with a real person keeping Explorer focused - clean
  full-chain success on one run, a clean mid-motion abort on another. Found
  and fixed one real bug along the way: `services/character/walk_signal.py`'s
  `wait_for_arrival()` was synchronous (`time.sleep()` inside an `async def`
  with no real `await` point), which meant the abort hotkey had nothing to
  land on during the arrival-wait phase specifically - the kill switch would
  not have worked during that window. Fixed by making it genuinely `async`
  (`await asyncio.sleep()`), re-verified against the same live abort test.
  **Self-focus, built and empirically verified rather than assumed**: the
  sequence originally only worked if the user had already clicked into the
  target app first - real autonomous use ("open the bracket file") can't
  depend on that. Added a focus step (`tools/_computer_uia.py`'s
  `focus_window()`) that runs right before the existing live foreground
  re-check, not instead of it - same safety property, just who establishes
  the precondition changes. Tested directly whether a bare
  `win32gui.SetForegroundWindow()` from this background process actually
  works, per explicit instruction to report the real answer rather than
  assume: it doesn't reliably - a real, repeated test hit Windows' documented
  foreground-lock protection (error 258, "the wait operation timed out").
  Fixed with the standard legitimate workaround, not a hack around the
  restriction: one real synthetic Alt keypress sent first (the same
  scan-code-resolved `keybd_event` mechanism the kill-switch build already
  established as load-bearing), which registers "recent input" with the OS -
  one of Windows' own documented allowance conditions. Verified 3/3 with the
  fix in place. User independently re-ran the full e2e test afterward and
  confirmed both the focus step and the walk phase worked live, unprompted:
  "I pressed Enter with the terminal still focused and it proceeded anyway,
  so she foregrounded Explorer herself."
  **"Open the bracket part" (no path given) - tested through the real
  `agent.run_agent()` loop, not by calling `computer` directly, per explicit
  instruction: "so this may be less about new capability than about whether
  the loop actually does it."** First real result was a clean failure, not a
  success: given only the vague description, she called `ask_user` on the
  very first turn - `logs/agent.jsonl` showed zero `list_dir`/`read_file`
  calls anywhere in the trace. Diagnosed per the user's own steer ("A8 found
  spec wording was the lever for list_dir, and A10 found the same for
  ask_user, so that's the first place I'd look") - and it was, but not the
  instruction text first tried. Adding a "search before asking" clause to
  `agent.py`'s `_TOOL_USE_INSTRUCTION` (the merged system-prompt text) alone
  changed nothing, re-tested in isolation from `persona.md` to rule out
  competing instructions - still a direct `ask_user` call, zero searches. The
  real lever was `tools/ask_user.py`'s own spec `description`, which
  literally named "a filename" as canonical grounds to ask - a closer, more
  specific match to the model's decision than a paragraph in the system
  prompt. Rewording it to exclude a filename that hasn't actually been
  searched for yet got real `list_dir` calls firing - but exposed a second,
  narrower gap: the model checked `cad/generated` (empty), got a dead end,
  and asked instead of also trying `cad/verified`. One more spec clause
  (`_TOOL_USE_INSTRUCTION`: "one empty or irrelevant directory doesn't mean
  the search failed... don't stop at the first dead end") fixed that too, on
  the next trial - but the trial after *that* one skipped search entirely
  and guessed a path directly (`computer` called with `path="bracket part"`,
  a string that isn't a real path at all), exposing a real, separate tool
  bug while doing it:
  `computer`'s `action="open"` branch never checked whether `path` actually
  existed before invoking `explorer.exe` on it - the exit-code-is-
  informational-only handling (needed for real success, see above) had no
  accompanying reality check, so a hallucinated path was reported as a false
  "Opened" success. Fixed by verifying `path` resolves to something real
  before ever invoking the open command (CLAUDE.md rule 6 - verify before
  declaring done - applied to a tool's own return value, not just human
  verification). **With every fix in place, ran the identical test three
  times to get an honest reliability read rather than trusting one green
  run**: 2 of 3 produced the full correct chain (`list_dir(cad)` ->
  `list_dir(cad/generated)` -> `list_dir(cad/verified)` -> `computer(open,
  explorer, "cad/verified/bracket")`); the third reverted to an immediate
  `ask_user` with zero searches, same as the original failure. **Honest
  answer to "where does it break": both named causes were real, not one or
  the other.** Spec wording was a genuine, fixable lever (ask_user's own
  description was actively inviting the failure it now avoids), but even
  with the clearest wording found, multi-step search-before-guess isn't
  deterministic - it now succeeds roughly 2/3 of the time, not every time,
  which lines up almost exactly with A5a's independently-measured ceiling
  for other persona/instruction-driven behaviors on this model. Not chasing
  a fourth wording pass to close that last third - this project's own A5a
  precedent ("two different rule phrasings converging on the same rate is
  real evidence the lever isn't persona wording") applies here too once a
  fix has already produced a real, measured improvement without reaching
  100%.
  **`find_file` (`tools/find_file.py`): removed the multi-step search
  reasoning from the model's job entirely instead of continuing to instruct
  around its ~2/3 ceiling.** The chaining reliability finding above was a
  real model ceiling, not a wording problem left to fix - so the follow-up
  wasn't a fourth prompt rewrite, it was making the task itself need fewer
  reasoning steps. `find_file(query)` does the recursive whitelisted-directory
  walk in code (`tools/_fs.py`'s existing `load_whitelist()`, same whitelist
  `list_dir`/`read_file` already use - no new directory becomes reachable),
  matching every relative path under it against all of the query's words
  (case-insensitive substring, all words required) and returning paths only -
  same "constrain the shape, don't add capability" discipline as every other
  tool here. "open the bracket part" becomes one `find_file` call plus one
  `computer` call instead of a chain of `list_dir` calls that can bail out
  early. Re-ran the identical three-trial test with `find_file` registered:
  **3 of 3** now resolve the correct file (`cad/verified/bracket/part.py`) in
  a single `find_file` call, zero wasted or wrong-branch searches, zero
  reversion to `ask_user` - up from 2/3 chained `list_dir` calls. One
  trial diverged in a different, orthogonal way worth noting honestly: it
  called `read_file` instead of `computer` on the correctly-found path,
  reading and summarizing the file's contents instead of launching it in
  Explorer - a genuine ambiguity in what "open" means for a `.py` file
  (show me its contents vs. launch it in an app), not a search failure -
  `find_file` itself found the exact right file 3/3.
