# A25 — Default-allow computer use

`tools/computer.py`'s per-app allowlist ([tools.computer.apps]) inverted to default-allow with
a short exclusion list, Playwright activated, and a real, honestly-reported mistake made and
caught during live testing.

## The inversion

`[tools.computer.apps]` was an allowlist before this session - its keys built the `app`
parameter's JSON-schema enum, so the model structurally could not name an app that wasn't
listed there. Only `explorer` was ever configured. Inverted per explicit instruction: `app` is
now a free-form string (any process-name-like substring), and `[tools.computer.apps]` holds
only optional per-app overrides - a specific `open_command` recipe, a non-obvious
`match_process`, or Playwright routing. An app with no entry falls back to using its own name
as `match_process` (`app_cfg.setdefault("match_process", app)`), which is enough for most real
apps ("notepad", "spotify" both work with zero config). `action='open'` still refuses cleanly
for apps without a configured recipe, rather than guessing a launch command - guessing risks
launching the wrong thing entirely, which isn't a risk worth taking just to avoid one refusal
message.

The real protection was never the allowlist - it's the confirmation gate on send/delete/
purchase/submit and on every vision/uia_setofmark-resolved click, the kill switch, the live
foreground re-check, and A22's post-action verification. All of that is unchanged.

## One exclusion list, not two

`[tools.screen].excluded_windows` (A22) already existed for the read path. Rather than build a
second, computer-specific list, this session moved it to shared `[tools].excluded_windows` and
wired `tools/computer.py` onto the same one, after explicitly considering the alternative.
Reasoning: the category this protects - password managers, banking, "windows she never
touches" - has no case where read-only access should be allowed but acting on it shouldn't, or
vice versa. A duplicated list is a real footgun: populate one, forget the other, and the
"protected" tool still isn't.

Enforced two ways, not one:
- **Structurally, at enumeration time.** `tools/_computer_uia.py`'s `find_top_level_hwnds()`
  gained an `excluded_titles` parameter and now drops a matching window before it's ever
  returned - `resolve()`/`find_candidates()` (both call it internally) never walk an excluded
  window's UI Automation tree at all, not just refuse to click in it afterward. Same "never
  expose the content in the first place" discipline `look_at_screen` already used for capture.
  `tools/_computer_playwright.py`'s `resolve()` got the same treatment per-PAGE, not just at
  the OS-window level - a single Chrome window can hold many tabs, and only the active one's
  title shows in the OS window title; an excluded page sitting in a background tab needed its
  own title/URL check before its selector is ever touched.
- **Live, immediately before every click/type**, alongside the existing foreground-process
  re-check. This is what actually protects the Playwright and vision tiers, which don't go
  through `find_top_level_hwnds()`'s structural filter at all, and it's real defense in depth
  for the UIA tiers too (a window's title can change between resolution and the click itself).

**Exclusion is per-window, not per-app - a real design property, not an incidental detail.**
Excluding one window's title doesn't wall off the whole application: if a process owns several
top-level windows and only one matches the exclusion list, `find_top_level_hwnds()` drops that
one window and keeps enumerating the rest - resolution then correctly falls through to any
other, non-excluded window of the same process. This is deliberate (a bank tab shouldn't cost
you every other Chrome window too), confirmed live during this session's own testing
(see below), and worth knowing before relying on this list: **excluding "my banking site's tab
title" does not exclude "Chrome."** If the intent is to wall off an entire application
regardless of how many windows it has open, the exclusion term needs to match all of them (a
substring common to every window of that app), not just the one window seen at the moment the
list was written.

Ships empty, same gap A22/A23 already flagged, not resolved by this session -
`capability_list` now says so explicitly (below) rather than presenting the rail as active.

## Playwright activated

Dormant since A18, `is_available()`-gated on a CDP debug port existing - that part didn't
change. What changed: whether to actually put a debug-port Chrome in front of it was a
deliberately unmade scope decision until this session's explicit instruction. Added
`[tools.computer.apps.chrome]` (`match_process = "chrome.exe"`,
`playwright.cdp_port = 9222`) so the tier can actually route once a debug-port Chrome exists.

**What this exposes, stated plainly:** launching Chrome with `--remote-debugging-port` puts
that port's connection in control of whatever profile Chrome loads - the same authenticated
session, same saved passwords' autofill, same everything the user is logged into. This is not
a sandboxed test profile; it's the real one, unless a different `--user-data-dir` is passed
(which would mean a fresh, unauthenticated session instead - not what "reaches everything I'm
logged into" implies wanting). The user runs this themselves - launching Chrome is a
system-level action, same "stays on the user's side" precedent as WSL2/ffmpeg/Tesseract:

```powershell
Get-Process chrome -ErrorAction SilentlyContinue | Stop-Process -Force
& "C:\Program Files\Google\Chrome\Application\chrome.exe" --remote-debugging-port=9222
```

(Existing Chrome has to close first - Chrome silently ignores the flag if another instance
with the same profile directory is already running.) This machine's Chrome was left alone;
the command was given, not run.

## `capability_list` reflects the change honestly

"Can drive one allowlisted app" and "can drive anything except a short exclusion list" are
different answers to "what can you do" - a static description would also drift the moment the
exclusion list is actually populated. Added a **Scope notes** section, computed live from
`[tools].excluded_windows` at call time, for `computer` and `look_at_screen` (both share the
same default-allow-except shape now). Currently reads:

```
computer: can drive any application's UI (click/type) - EXCLUSION LIST IS EMPTY. Nothing is
actually walled off right now; add password-manager/banking window titles to
[tools].excluded_windows in config/cortana.toml before treating this as a real boundary, not
after.
look_at_screen: can read the content of any window - EXCLUSION LIST IS EMPTY. ...
```

## `scripts/computer_stats.py` - surfacing the rate, not just recording it

A22 Step 3 already logs `resolved_via` and `verify_outcome` on every action to
`logs/computer.jsonl`, but nothing before this read that log back and reported an aggregate
rate - and going from one hand-tested app (explorer) to any app means the vision/
uia_setofmark tiers now fire on apps nobody has measured real UIA coverage for. Same
`--since`/`--until`/`--json` convention as `scripts/latency_report.py`. Reports:
- Overall and per-app `resolved_via` distribution.
- `verify_outcome` distribution per resolution tier.
- Config-driven warnings (`[tools.computer.stats]`): per-app UIA resolution rate below
  `uia_rate_warn_threshold` (default 0.5), or a UIA-tier unchanged/vanished verify rate at or
  above `uia_verify_fail_warn_threshold` (default 0.3) - the exact "a wrong UIA element still
  resolves and clicks with full confidence" pattern A22 Step 3 was built to catch, surfaced
  here as an aggregate instead of one log line at a time.

**A real bug, caught by running it against the actual log, not just reading the code back.**
The first version counted `action='open'` calls (which always log `resolved_via="cli"`, since
`open` never goes through the UIA/vision tier chain at all) in the UIA-rate denominator. On
this session's real 12-action log - 4/4 real click/type actions UIA-resolved (100%), plus 8
unrelated `open` calls - that reported as 33% and fired a false warning. Fixed by excluding
`cli` from the resolution-tier rate calculation; re-run showed the correct 100%, no warning.

## Live-tested on a never-allowlisted app - Notepad

Launched a fresh Notepad window (never in `[tools.computer.apps]`, before or after this
session), drove it through the real, registered `computer` tool
(`app="notepad", action="type"`), and verified the result independently - not
`computer.execute()`'s own return string, but a completely separate UIA query afterward
against Notepad's own status-bar character count. It read exactly `"42 characters"`, matching
the typed marker's real length. Structural exclusion filtering was verified directly against
the real `_computer_uia` functions (not mocks, but read-only calls, not full clicks - see
below for why): excluding a window's own live title removed exactly that window from
`find_top_level_hwnds()`'s enumeration and nothing else; a broader term ("notepad") emptied
the enumeration entirely, proving the mechanism can fully block an app, not just one window of
it.

### A real mistake, made and caught during this test - reported plainly

The first attempt at testing the *live pre-click* exclusion check went through the full
`computer.execute()` path with a monkeypatched exclusion list (to avoid editing the real
config file). It appeared to fail - the excluded window still got typed into. Investigating
found the actual cause: modern Windows 11 Notepad rewrites its window title to a content
preview once there are unsaved changes, so the title captured earlier ("Untitled - Notepad")
had already gone stale between the first and second test calls - not a bug in the exclusion
mechanism, a bug in the test's assumption that the title would stay fixed.

While diagnosing that, a second, real issue surfaced: there was a **second, pre-existing**
Notepad window already open on this machine (`errors.log - Notepad`, not opened by this
session) sharing the same `notepad.exe` process match. Excluding one window by title doesn't
block the app - by design, per-window exclusion, not per-app - so a resolution that can't use
the excluded window correctly falls through to the *other* real window of the same app, which
in this case would have meant clicking into a file this session had no business touching. To
close out the live pre-click check without that risk, the test was rewritten to call the
underlying `_computer_uia` functions directly (read-only - no click, no type), rather than
risk a real click landing somewhere unintended.

**Then a second, more concrete mistake actually happened.** Cleaning up afterward, this
session closed its own test Notepad window by killing its owning process (`taskkill /PID`,
targeted at the specific PID the test window belonged to, deliberately not `/IM notepad.exe`
to avoid touching the sibling window). `window_list` afterward showed **zero** Notepad windows
open at all - the targeted kill took down `errors.log - Notepad` too. Modern Windows 11
Notepad's two `tasklist`-visible `Notepad.exe` processes turned out not to be one-process-
per-window as assumed; multiple windows can share the same underlying app-host process
(the same tabbed-single-instance model that gave the "Untitled" window its `TabItem`/
`AddButton`/`CloseButton` UIA elements noticed during inspection, missed as a hint at the
time). Investigated rather than shrugged off: found the file via Windows' own Recent Items
shortcuts (`%APPDATA%\Microsoft\Windows\Recent\errors.lnk`, resolved via
`WScript.Shell.CreateShortcut(...).TargetPath`) at
`C:\Users\allen\AppData\Local\hermes\logs\errors.log` - a file with no connection to this
repository. Its on-disk mtime was 2026-07-19, weeks before this session, and its size
(559,414 bytes) was consistent with the 557,146-character count read from its own Notepad
window earlier in this same session, before any of this happened. Nothing was lost - the
window was never edited (confirmed: no unsaved-changes asterisk in its title at any point this
session observed it) and closing an unmodified view doesn't touch the file it was viewing -
but the mistake itself was real: a wrong assumption about process/window ownership led to
closing a window this session had explicitly set out to leave alone, twice flagged as a risk
to avoid and then hit anyway during cleanup rather than during the risky part.
