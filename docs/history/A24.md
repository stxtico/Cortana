## Verification: no Office on this machine, so external checks had to substitute

Per explicit instruction, every writer got checked against something external, not its own
return string — the same discipline that caught three silent A23 failures. A one-off script
(not committed - scratch, see `$CLAUDE_JOB_DIR/tmp`) called each tool's `execute()`, then:

- **docx/xlsx/pptx**: re-opened the output with `python-docx`/`openpyxl`/`python-pptx`
  (the same libraries that wrote them) and diffed the read-back title/paragraphs, sheet
  name/rows, and slide titles/bullet content against what was written. Also confirmed each
  is a real, well-formed zip (`zipfile.is_zipfile()` plus checking for `word/document.xml`/
  `xl/workbook.xml`/`ppt/presentation.xml`), since all three formats are zip containers
  underneath and a broken writer could plausibly produce a file that "looks" written by
  duration/size alone.
- **pdf**: `reportlab` has no reader of its own, so `write_pdf`'s output was checked via this
  same session's `pdf_read` — round-tripped the title, a plain paragraph, and a paragraph
  containing a literal `&` (to confirm the XML-escaping in `write_pdf.py`'s docstring
  actually works, not just that it doesn't crash).

## pdf_read

`pdfplumber`, not a raw text-layer extractor — `PROMPTS.md` asks for "text and tables"
explicitly, and pdfplumber's `extract_tables()` gives real rows; a table flattened through
plain text extraction reads as a run of misaligned words. Read-only, same
`[tools].whitelist_dirs` as `read_file`/`list_dir`.

## ocr — built, self-gating, not live-verified (Tesseract isn't installed)

`tools/_ocr.py` (shared helper) + `tools/ocr.py` (agent-callable). `is_available()` calls
`pytesseract.get_tesseract_version()`, which actually invokes the `tesseract` binary as a
subprocess — checked live that this matters: `pytesseract` imports fine with zero Tesseract
installed at all (it's a pure-Python subprocess wrapper), so a naive "does the import
succeed" check would have reported this tool available when it structurally cannot run.
Confirmed dormant right now: `where tesseract` finds nothing, and `ocr.is_available()`
returns `False`.

**To activate:** `winget install --id UB-Mannheim.TesseractOCR` (system-level install, left to
the user per the WSL2/ffmpeg/CortanaShell precedent — this project doesn't silently reach
outside its own directory to install system dependencies).

**Never falls back to vision when unavailable** — per explicit instruction, a confident wrong
transcription from a tier already measured fabricating (see CLAUDE.md's Known model
limitations) is worse than reporting the honest gap. `ocr` just doesn't appear in
`capability_list`'s available set until the binary exists; nothing routes around it.

Because the binary genuinely isn't present, OCR's actual text-extraction accuracy is
unverified this session — a real, stated gap, not glossed over. Once Tesseract is installed,
re-run: extract text from a known-content test image and confirm it matches exactly, the
same standard every other tool here was held to.

## OCR wired into `look_at_screen` — a third, exact tier

`tools/screen.py`'s tiering was UIA (exact) → vision (interpretive, hedged). Added OCR as
exact-but-narrower-than-UIA: UIA reads the accessibility tree (control names, labels — not
text baked into pixels), OCR reads the screenshot itself, catching cases like a screenshot
displayed inside a viewer, a rendered PDF, or a canvas/game UI where nothing exists in the
accessibility tree at all. Vision's prompt was reworded to explicitly defer text
transcription to UIA/OCR and focus on layout and visuals — the same "don't ask the weak
tier to do the strong tier's job" discipline A22 established for UIA over vision.
Refactored the screenshot capture into one call reused by both OCR and vision (previously
vision alone captured; capturing twice for two consumers would've been wasteful and
pointless when the frame doesn't change between them). Live-verified end-to-end against a
real window (this session's own terminal) — UIA and vision tiers both still produce
identical-shape output to before; the OCR tier is correctly and silently omitted since it's
still dormant, not attempted-and-failed.

## email_draft — real, self-gating, dormant (Outlook not running)

Reuses `tools/_outlook.py`'s existing `is_available()` (process-running check, then
`GetActiveObject` — never `Dispatch`, never launches Outlook, per CLAUDE.md rule 10) and adds
a new `get_application()` helper alongside the existing `get_namespace()`, since
`CreateItem()` (needed to build a `MailItem`) lives on the `Application` COM object, not the
namespace `calendar_read`/`email_read` already use. `execute()` sets `To`/`Subject`/`Body`
and calls `.Save()` — there is no `.Send()` call anywhere in this module, not a flag
defaulted off. `REQUIRES_CONFIRMATION = True`, same as every other write tool. Confirmed
dormant right now (Outlook isn't running in this session): `email_draft.is_available()`
returns `False`.

## copy / move / rename / delete

All four resolve both source and destination (where applicable) through
`tools/_fs.py`'s existing `write_whitelist_dirs` — no second path check invented, per
explicit instruction. `delete` uses `send2trash`, never `os.remove`/`Path.unlink`/
`shutil.rmtree`. All four `REQUIRES_CONFIRMATION = True`.

Live-verified against real files in `deliverables/`, checking actual filesystem state after
each call rather than trusting the return string:
- `copy`: source persisted, destination created with matching content.
- `move`: source gone, destination created with matching content.
- `rename`: old name gone, new name present, content preserved.
- `delete`: gone from its original location, **and** — the check that actually matters for
  "goes to the recycle bin, never unlink" — genuinely present in the Windows recycle bin,
  confirmed via `Shell.Application`'s `Namespace(10)` COM enumeration, not inferred from the
  file's absence alone (a permanent delete would look identical from that angle). First
  attempt at this check false-failed: the recycle bin's shell view returns display names
  *without* their extension (`renamed-x` for `renamed-x.txt`), not a bug in `delete.py`
  itself — fixed the check, not the tool, once the real cause was confirmed.

11/11 checks passed. Test artifacts cleaned up from `deliverables/a24_verify_fs/` after
confirming; the recycle-bin entry itself was left alone, matching what a real delete does.
