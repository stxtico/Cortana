# A14 — CAD generation with a verification loop

Moved verbatim from CLAUDE.md's Done log (2026-08-12 restructure) — see
CLAUDE.md's Done log for the one-line pointer back to this file.

- **A14 — CAD generation with a verification loop (`tools/cad.py` +
  `tools/export_step.py`/`export_stl.py`).** Checked the load-bearing
  assumption before building anything around it, per explicit instruction:
  "vision is gemma4:e4b itself" turned out **false**. `/api/show` reports
  `"vision"` in e4b's capabilities, but three real request shapes
  (`/api/chat`, `/api/generate`, the OpenAI-compat endpoint) all failed
  identically - e4b's own reasoning trace on the third showed it received
  an "Image Placeholder/Empty Input" token, not real pixels. Root-caused,
  not just worked around: e4b's Modelfile `TEMPLATE` is bare `{{ .Prompt }}`
  with no `.Messages` iteration at all - tool-calling still works (already
  extensively verified this project) only because Ollama's custom
  `RENDERER gemma4`/`PARSER gemma4` hooks handle that internally, but
  evidently don't thread image data through. Confirmed it wasn't a
  client-side bug by running the identical code against `gemma3:12b`
  (already pulled, real vision support, proper `.Messages`-templated
  Modelfile) - correctly described the same render. Landed as
  `[models].vision = "gemma3:12b"`, swapped in via the same deliberate
  keep_alive mode-boundary pattern already measured and accepted for
  heavy/CAD work (8-13s cold load, fine for a multi-second generation
  loop, never fine for real-time voice turns) - not resident alongside the
  conversational stack. `services/brain/client.py`'s `stream()` gained
  optional `model`/`format` parameters (backward compatible - existing
  callers pass neither) so this reuses the one shared httpx client rather
  than a second raw-request path.
  **A live test run reframed the vision step entirely, mid-build.** First
  attempt let a vision "looks wrong" verdict feed back into the revise loop
  same as a geometric failure. Real testing (not hypothetical) showed the
  actual failure mode: asked to critique, the model fabricated specific
  wrong claims rather than admitting uncertainty - the same behavior
  pattern the A5a persona pushback investigation already found (padding/
  unsolicited specifics measured at roughly two-thirds reliability, not a
  fluke). Inverted the authority relationship in response: geometric
  validation (`scripts/_cad_common.py`'s `verify_solid()`, reused from A13
  unmodified in its default call shape) is ground truth; vision is a weak
  secondary signal, restricted to what a measurement can't express (does
  the overall shape match, is a feature obviously misplaced/missing),
  explicitly given a real "cannot tell" abstention option, and never asked
  about anything the validator already measures exactly. Verified this
  framing actually works, not just reads better: the same correct
  render+description pair passed 4/4 consecutive vision calls with zero
  contradiction, and a deliberately mismatched description was correctly
  flagged - real discrimination, not blind approval.
  **Reused A13's executor, extended it rather than forking it** (explicit
  instruction). `verify_solid()` gained an optional `min_wall_mm` parameter
  (default `None` - A13's `cad_synth.py` call sites are unaffected, same
  speed characteristics as before) backed by a genuinely new, tested
  technique: an inward OCCT boundary offset
  (`BRepOffsetAPI_MakeOffsetShape`) at the threshold distance, checking the
  result stays a valid solid via `BRepCheck_Analyzer` - `IsDone()` alone
  tested empirically permissive (stayed `True` on a solid with a known
  ~0.1mm floor). Confirmed directionally correct on three real cases before
  trusting it: a deliberate ~0.1mm-floor solid failed around -1.0mm; a
  uniform 10mm box passed everything up to the geometric half-thickness
  (-4.9mm) and failed just past it (-5.5mm); the real L-bracket (4mm
  nominal wall) failed around -2.0mm - conservative relative to nominal
  (the multi-face offset hits the inner corner/fillet region first), the
  right direction for a safety check to be imprecise in. 8ms per probe -
  no meaningful cost added per iteration. `bounding_box_mm()` also added
  for the "dimensions match what was stated" requirement -
  `_check_dimensions_match()` compares stated vs. built extents by
  *magnitude* (largest-to-largest, etc.), deliberately not by asserting a
  specific dimension-name-to-axis mapping, which isn't generically knowable
  for arbitrary generated code.
  **Unit checking, structural not advisory**: every `dimensions` value must
  be a unit-tagged string (`"40mm"`, `"0.25in"`) - `tools/_cad_units.py`'s
  `validate_dimensions()` converts everything to mm *in Python*, before a
  single number reaches the model's generated code, which prevents
  mixed-system arithmetic bugs structurally (the model never sees a raw
  inch value to accidentally combine with a raw mm value) rather than
  trying to pattern-match the bug after the fact in unitless CadQuery
  literals, which would mean guessing which convention each number was
  meant in. A bare number (or unrecognized unit) is refused immediately,
  before touching the model at all, with a message naming exactly which
  dimension needs a unit.
  **ask_user verified as a real prerequisite, not just documented as one.**
  `cad_generate`'s schema makes `dimensions` required and every value
  unit-tagged, so the model structurally cannot call it without having
  already gathered explicit numbers - and a live `run_agent()` test (fake
  input handler standing in for real stdin/mic, fake `speak_stream` standing
  in for real TTS audio, since neither is available headless here) proved
  the actual behavior: given "Make me a mounting bracket" (no dimensions at
  all), the model asked a genuinely specific real clarifying question
  first (size, mounting context, hole pattern) *before* attempting
  `cad_generate` even once, then correctly parsed the free-text answer
  ("30mm wide, 20mm tall, 3mm thick, 4mm holes...") into properly
  unit-tagged dimensions for the actual tool call - confirmed via
  `logs/agent.jsonl`, not just inferred from the final result.
  **A real bug found by a genuine end-to-end test, not a synthetic one -
  and it's the reason this tool doesn't silently produce wrong parts.**
  First full run (four-hole flange): geometric validation and dimension
  matching passed on every one of 4 iterations, vision approved iteration
  4 outright ("shape_matches: true", nothing flagged) - and the exported
  STEP file, independently re-imported and rendered, had exactly **one**
  hole, not four. Root cause: the generated code's hole-cutting loop called
  `cq.Workplane("XY").translate((x, y, 0))` on a freshly-created, empty
  workplane before sketching - `.translate()` moves objects already on the
  stack, not where later sketching happens, so all four "different"
  cutter positions silently collapsed onto the same spot. Neither
  `isValid()`, volume, STEP-export success, nor the bounding-box check
  were ever going to catch this (a single-hole plate is watertight, has
  correct volume, and has the correct overall bbox) - and vision missed it
  too, a real, demonstrated false negative in exactly the "hole count"
  category the design had assumed geometry alone would cover, but hadn't
  actually implemented. Fixed with a genuinely new, tested check:
  `count_inner_wire_loops()` (sums inner wire loops across every face - a
  through-hole contributes one per face it exits through, confirmed
  discriminating cleanly: 2 loops on the broken single-hole part vs. 8 on
  a correctly-cut four-hole one) plus an optional `feature_counts`
  parameter (e.g. `{"holes": 4}`) checked with `>=` against a declared
  count - an honest lower bound, not a claim of exactness this technique
  can't generically guarantee. This became a cheap, pre-vision geometric
  gate, exactly matching the design's own stated authority order (never
  spend a vision call on something geometry can check directly). Retested
  with the fix and `feature_counts` declared: caught a **second, different**
  bug on the very next run (corner-relative hole coordinates computed
  against a corner-origin convention, but `cq.Workplane().box()` centers at
  the origin by default, so 3 of 4 holes landed outside the material and
  silently cut nothing) - the tool correctly reported honest failure after
  exhausting all 5 iterations rather than falsely claiming success, exactly
  the right behavior for a case it couldn't resolve. Added a second
  evidence-based (not speculative) system-prompt clarification about
  CadQuery's box-centering convention; retested once more and it converged
  in 2 iterations to a genuinely correct four-hole part, independently
  re-verified (STEP re-import, wire-loop count, and a fresh render actually
  looked at).
  **Done-when, verified for real, full path**: a live `run_agent()` call
  with an ambiguous request ("Make me a mounting bracket") correctly
  triggered `ask_user` before any generation attempt, the free-text answer
  was correctly parsed into unit-tagged dimensions, `cad_generate` ran to
  a verified part in 2 iterations, and the exported STEP file - re-imported
  fresh via CadQuery, independent of the generation pipeline's own claims -
  came back valid with a bounding box matching the stated dimensions
  exactly (30x20x3mm).
  **Scope stated honestly, matching PLAN.md's own instruction**: both
  `cad_generate`'s tool description and `tools/cad.py`'s module docstring
  say plainly that this works for prismatic parts with clear features and
  stated dimensions (brackets, enclosures, plates, mounts) and does not
  work for organic shapes, complex assemblies, or reverse-engineering a
  real object to tolerance from a photo alone - stated in the tool
  description itself, not just in comments, so the model sees the same
  boundary a human reading the code would.
  `export_step`/`export_stl` built as their own standalone tools (not just
  `cad_generate`'s automatic final step, which still happens) - for
  re-exporting anything already in `cad/generated/` or `cad/verified/`
  without re-running the generation loop; `cad_generate`'s success path now
  also writes a canonical `part.py` (the winning iteration, not
  `iteration_N.py`'s name) specifically so a good generated result is
  directly promotable into `cad/verified/` via `scripts/cad_log.py add-part`
  with no renaming step. `cad/generated/` gitignored, same "derived/working
  state stays out of git" pattern as `cad/dataset.jsonl`.
