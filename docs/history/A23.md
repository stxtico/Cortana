## notify — the missing daemon output, plus a real caught failure

`tools/_notify.py` (winotify-backed Windows toast) + `tools/notify.py` (agent-callable) +
wired into `services/daemon/output.py`'s `announce()` alongside the existing CLI print, per
explicit instruction (A11 already built triggers/relevance/rate-limiting; this was the
missing output, not a new system).

**Live-testing this caught the exact failure shape flagged going in.** A first `notify.execute()`
call returned cleanly with no exception, but a real screenshot taken immediately after showed
no toast anywhere on either monitor. Rather than trust the non-exception return, tested
against a genuinely registered AUMID (`Windows PowerShell`, pulled from `Get-StartApps`) to
rule out an app-registration problem — still nothing. Root cause, found by reading raw
registry state: `HKCU\...\PushNotifications\ToastEnabled = 0` — Windows notifications were
disabled system-wide on this machine (Settings > System > Notifications), unrelated to any
app registration. Not corrected here — flipping a systemwide OS setting was explicitly left
to the user, not this session's call to make. Instead: `tools/_notify.py` gained a real
`toast_enabled()` check (reads that registry key directly, fails open on an unreadable key),
`tools/notify.py`'s `execute()` now reports the honest state ("notification sent, but Windows
notifications are disabled system-wide... it will not actually be visible"), and
`services/daemon/output.py`'s new notify path falls back to a CLI print of its own when toasts
are off or fail — so a proactive daemon never silently discards what it wanted to say, per
explicit instruction.

Left `[tools.screen].excluded_windows` (A22) unaddressed by this session, per the user's own
flag going in — still empty, still doing nothing until populated, unrelated to this wave's work.

## media_keys — a verification bug that mattered, caught by the user, not this session

`tools/media_keys.py`: play_pause/next/previous via `win32api.keybd_event` with scan-code
resolution — the same pattern already proven in `tools/_computer_uia.py`'s `focus_window()`
(A18/A22), not the `keyboard` package's own `send()`.

**The first verification pass in this session was wrong, and the mistake is worth recording
plainly.** Screenshot-based verification against Spotify failed for an unrelated, real
reason (`PIL.ImageGrab.grab(bbox=...)` returns solid black for a negative-origin window rect
on this machine's dual-monitor layout; Spotify's own UI also turned out to show a chrome-less
"now playing" view with no persistent transport bar to diff anyway). Pivoted to SMTC (the
System Media Transport Controls API, the real source both apps and Windows' taskbar widget
read from), queried via PowerShell's WinRT bridge — but the test only read *a* session's
`PlaybackStatus` before and after, never its *identity*. A `Playing → Paused → Playing`
round trip looked clean and was reported as "a genuine, authoritative state change." It
wasn't: the first key press paused a real YouTube tab; the "restore" key press, sent without
re-checking who was actually current, hit Spotify instead — two different apps, left in a
state the user didn't ask for (a video silently left paused, a different app's music
resumed). The user caught this from the actual audio, not from anything this session
checked.

**First fix attempt was also wrong, and worse in a specific way: it asserted confidently
instead of hedging.** `tools/_smtc.py` (new) added `all_sessions()` (app + status for every
session SMTC knows about) alongside `current_session()`. The first pass at using it made
`media_keys.execute()` record the active app before sending a key, then re-check that ONE
specific app's own session afterward - fixing the "current reassigns to an untouched app"
trap (live-verified: a key correctly paused YouTube, but the very next `current_session()`
query had already handed "current" to an untouched Spotify). Re-tested, and it reported
`"Confirmed: affected 'Spotify.exe' (Paused -> Playing)"` - but on that test run, **YouTube
had also changed state, from Playing to Paused, at the same time**, and the single-app check
had no way to see it, because it only ever looked at the one app it already knew about
beforehand. Checking one specific app instead of "current" was a real improvement over the
first bug, but still had the same shape of bug: narrow scope reporting false confidence.
Caught immediately (not by the user this time) by comparing against an independent
`GetSessions()` dump showing every session, which the single-app check never consulted.

**Fixed by diffing every session that existed before or after, not one.** `execute()` now
snapshots `all_sessions()` before and after the key, and compares the full set: zero changed
sessions is reported as "may not have reached anything"; exactly one changed session is
reported as confirmed *only if* it matches the app that was active beforehand (and flagged as
an unexpected-target mismatch if not); **more than one changed session is reported as
exactly that - every app that changed, plainly, not a single picked "winner."** The tool's
own spec() description now says outright that a single press can affect more than one app at
once on this machine, confirmed, not hypothetical.

**Re-tested with the properly-fixed check, honest setup (YouTube playing, Spotify already
paused - the machine's real state at the time, not engineered), single call, no restore
key sent afterward, cross-checked against an independent `GetSessions()` dump both times.**
Result: `"Confirmed: affected 'Chrome.UserData.Profile1' (Playing -> Paused)"` - Spotify's
own session showed no change, matching the tool's report exactly. This run did **not**
reproduce the earlier two-sessions-at-once behavior; that doesn't mean the earlier finding
was wrong, only that it wasn't reproduced on this one additional trial - left as an open,
real, unexplained characteristic of this tool on a multi-source machine, not resolved and
not smoothed over. Considered and rejected, unchanged from the first pass: an `app` parameter
that focuses a target window first - SMTC session routing tracks playback activity, not
window focus, so it wouldn't redirect anything and would be a false promise.

## process_list

`tools/process_list.py`, via psutil (already a direct dependency since A21's workers).
`psutil.Process.cpu_percent()`'s well-documented first-call-returns-0.0 behavior (no prior
call to measure a delta against) is handled for real: every process is primed with one
throwaway call, then re-measured after a real, configurable wait
(`[tools.process_list].sample_interval_s = 0.3`) — live-verified output shows real, varied,
non-zero CPU% values across processes (not a uniform, misleading 0.0), and sorting by memory
vs. CPU produces genuinely different, correct orderings.

## window_list

`tools/window_list.py` reuses `tools/_computer_uia.py`'s `find_top_level_hwnds()` (A22 Step 1's
own real-window enumeration) with an empty `process_match` string — the function's own
substring filter (`process_match.lower() not in proc_name.lower()`) means `""` matches every
process for free, no change to that function needed. Live-verified against the real desktop:
correctly listed a real YouTube tab title, Spotify, this session's own terminal window, and
two independent "Settings" windows from different owning processes.

## search_content

`tools/search_content.py` - literal, case-insensitive substring grep across
`tools/_fs.py`'s whitelisted directories (the same whitelist `read_file`/`list_dir` already
use), not regex - the realistic ask ("find the file with this phrase/number in it") doesn't
need it, and literal search can't misinterpret special characters in an invoice number or
email address. Binary/oversized files are skipped (`[tools.search_content].max_file_size_bytes`,
a null-byte sniff test), results capped (`max_results = 50`). Live-verified: found a real,
just-added config key (`excluded_windows`) at its exact file and line number, and correctly
reported zero matches for a string that doesn't exist anywhere in the whitelist.

## transcribe_media

Added `Transcriber.transcribe_file(path)` to `services/ears/stt.py` (refactored the shared
segment-to-`Transcript` logic into `_run()`, called by both the existing mic-audio
`.transcribe()` and the new file-path `.transcribe_file()`) — passes the path straight to
faster-whisper's own `WhisperModel.transcribe()`, which decodes audio *and* video files itself
via its bundled PyAV pipeline, no manual PCM pre-decoding needed.

`tools/transcribe_media.py` holds its own lazy, module-level singleton `Transcriber`
(CLAUDE.md rule 7: one persistent instance per process) configured identically to the live
ears pipeline's ([audio.stt] in `config/cortana.toml`) - not a literal shared object with
`services/ears/pipeline.py`'s instance, which is architecturally a separate process; "point
the already-resident Whisper at a file" means the same configured model/wrapper, loaded once
per whichever process actually calls this tool, not something literally reachable across a
process boundary. Path resolution goes through the same `tools/_fs.py` whitelist read_file
uses. Live-verified: transcribed a real reference voice recording
(`voice_refs/voice_ref_01.wav`, copied temporarily into the whitelisted `logs/` dir and
removed after) and got back accurate, coherent real speech text in 4.5s (including cold model
load); separately confirmed the whitelist boundary actually refuses a real file
(`voice_refs/voice_ref_01.wav` directly, outside any whitelisted directory) with a real
`PermissionError`, not a silent pass-through.

## capability_list

The one tool this session was explicitly told needed more care than originally specced:
"what can you do" has a trap where half these tools are dormant or gated, and presenting
everything as available would be actively misleading. Built to report three states -
available now, available-but-gated-behind-confirmation, and dormant-with-a-reason - sourced
from the real `services/brain/agent.py._ALL_TOOLS` registry and each tool's own live
`is_available()` call, never a hand-maintained list of names (which would silently drift the
first time a tool is added, removed, or its gating condition changes). The one genuinely
authored piece is the human-readable "why" for currently-known dormant tools
(`_DORMANT_REASONS`, a small dict) - a boolean carries no reason on its own, and a tool not
covered by that dict still gets an honest generic fallback rather than vanishing or crashing,
so a future gated tool without a specific entry degrades gracefully.

Import of `services.brain.agent` is deferred to `execute()` rather than done at module load
time - `agent.py` imports every tool module (including this one) to build `_ALL_TOOLS`, so a
module-level import back would be circular. Live-verified against the real, complete 28-tool
registry after full registration: 23 available now, `shell`/`write_file` correctly reported
as gated-behind-confirmation (and `shell`'s `is_available()` genuinely returned true, a live
confirmation A9's WSL setup is actually working on this machine), and `web_search`/
`calendar_read`/`email_read` correctly reported dormant with accurate, specific reasons.
